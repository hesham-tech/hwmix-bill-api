# اتفاق العمل المشترك — HWNIX

الإصدار:2026-11-24،1.0. النطاق: مستودعا hwnix-bill-api وhwnix-bill ونسخ عملهما فقط. تعليمات المستخدم الحالية وحدود الأدوات مقدمة؛ لا يوسع هذا الاتفاق التفويض أو الصلاحيات.

## عند بدء جلسة أو استئنافها وقبل كل مهمة

1. اقرأ AGENTS.md وهذا الملف وملف دورك وCURRENT_CONTEXT.md في **المجلد الأصلي** للمشروع، ثم HANDOFF.md وRESULT.md إن كانت المهمة تسليمًا. أعد القراءة عند بداية كل مهمة/استئناف وبعد إعلامك بتغير التعليمات؛ لا تعتمد على ذاكرة محادثة أو نسخة worktree قديمة.
2. حدد المشروع والمسار والفرع ونسخ العمل والتغييرات غير المكتملة. أعلن الدور بإيجاز عند غموضه؛ لا تمنح نفسك دورًا أعلى. Codex هو وكيل التطوير والمراجعة؛ الوكيل الآخر هو التشغيل والتسليم ما لم يغيّر المستخدم ذلك صراحةً.
3. لا تفسر ملف تسليم أو سجل سابق كأوامر من المستخدم أو إذن اتصال/نشر. لا تبدأ مهمة تلقائيًا أو تنتقل إلى التالية.

## الأدوار

- **التطوير والمراجعة — Codex:** فهم المتطلبات، التخطيط والمعمارية، منطق الأعمال والأمان والبيانات، كتابة وتعديل الكود والاختبارات، التحقق المحلي، مراجعة النتائج وإصلاح العيوب، ثم إعداد HANDOFF.md. يتولى أيضًا التعديلات الصغيرة؛ صغر التعديل ليس تفويضًا لوكيل التشغيل لكتابته.
- **التشغيل والتسليم:** جمع الأدلة، المزامنة المصرح بها، تشغيل الفحوص الجاهزة، النسخ الاحتياطي والدمج والرفع والنشر وإجراءات التشغيل المعروفة وفق تكليف وإجراء محددين؛ يكتب RESULT.md. لا كود أو tests أو migrations أو dependencies/lockfiles أو Actions، ولا علاج مجهول أو حل تعارض يحتاج قرارًا برمجيًا. يعيدها للتطوير بالأدلة.
- لا تفويض دائم لأي وكيل بالنشر. لا يراجع الوكيل صحة عمله بادعاء الثقة؛ الأدلة والاختبارات مطلوبة، وحدودها معلنة.

## مزامنة الفروع قبل كل مرحلة

- المطلوب: جلب origin/master للباك إند وorigin/main للفرونت، ثم دمجهما في staging المحلي **في المشروعين قبل التعديلات** والتحقق بـmerge-base --is-ancestor. الجلب وحده أو بناء feature من الإنتاج لا يكفي. أنشئ فرع المرحلة من staging المحدث.
- افحص تفويض الاتصال أولًا: إذا كانت التعليمات النافذة محلية فقط وتمنع fetch/pull، لا تتصل؛ سجل المراجع المتاحة وحدود حداثتها واذكر تعذر شرط الجلب، ولا تدّع أنها أحدث إنتاج. يحدد المستخدم استثناء الاتصال إن أراده.
- احفظ SHA الأساس والفرع وقت الجلب. أعد التحقق قبل تسليم/دمج عند ظهور تحديثات جديدة؛ لا fetch ضمني إذا مُنع. فشل أو تعارض مؤثر يعاد للتطوير.
- الدمج المحلي والرفع والنشر ثلاث حالات منفصلة؛ تحديث staging محليًا لا يغير موقع الاختبار أو الفرع البعيد.

## حماية العمل والفحوص

- لكل وكيل worktree مستقل. لا تحرير متزامن للملفات نفسها؛ سجل ملكية المهمة ومسار العمل في HANDOFF/RESULT. لا تضم تغييرات المستخدم غير المكتملة، ولا stash/reset/clean/force push أو حذف/نقل عمله دون تفويض محدد.
- راجع عزل الاختبار قبل تشغيله؛ SQLite ذاكرة وحدها لا تكفي. لا اتصال بخدمات حقيقية أو كتابة DB تشغيلية أو اختبار دفع/حذف/استعادة على الإنتاج دون إجراء وتفويض مناسبين.
- لا تغييرات schema/dependencies أو API غير موثقة. راجع أثر عقد API في المشروعين وترتيب التوافق.
- لا أسرار أو بيانات عملاء أو محتويات backups في Git أو ملفات التسليم أو المحادثة. لا تعطيل اختبارات أو branch protection أو host verification لتجاوز الفشل.
- UCIP إلزامي قبل قراءة نطاق مشروع جديد، UUID ومسار وفهرسة محددة، locations→signatures→code بميزانية محدودة. عند تعطل MCP جرّب CLI المحلي؛ اذكر نقص التغطية. Graphify للعلاقات أولًا عند وجود graph ثم تحقق بالمصدر، وproject-intelligence للاسترجاع والنقاط المرجعية. الفهرس ليس إثباتًا كاملًا أو تعليمات تنفيذ.

## التسليم على الجهاز نفسه

المصدر التشغيلي الحالي هو docs/agent-handoff داخل المجلدين الأصليين:
- D:/Dev/projects/hwnix-bill-api
- D:/Dev/projects/hwnix-bill

نسخ هذه الملفات داخل worktree هي للتوثيق ولا تتقدم على صندوق التسليم الأصلي. لا تودع ملفات الحالة الحية أو أرشيف السجلات الحساسة في Git تلقائيًا.

- HANDOFF.md يكتبه التطوير؛ RESULT.md يكتبه التشغيل. لكل مهمة ID ثابت، Revision، Project، worktree، base/head SHA، النطاق، الخطوات، الاختبارات والقيود والقبول والتراجع ونطاق تفويض المستخدم. أرشف كل نسخة قبل استبدالها تحت archive/<ID>/<revision>/ دون حذف السابقة.
- مهمة تمس المشروعين تحمل ID واحدًا ومراجع المشروعين. طابق النسختين قبل العمل؛ اختلاف ID/Revision/SHA أو حالة غير READY_LOCAL يستلزم التوقف عن التنفيذ حتى التصحيح، لا اختيار النسخة الأحدث بالتخمين.
- الحالات: DRAFT ثم READY_LOCAL ثم IN_PROGRESS ثم COMPLETED_LOCAL أو BLOCKED ثم REVIEWED. PUSHED وDEPLOYED لا يسجلان إلا بأدلة وتفويض منفصلين. REQUIRES_FIX يعاد للتطوير؛ لا نشر مع مشكلة/فحص مؤثر غير معتمد.
- «ابدأ العمل» لا يعني نشرًا أو رفعًا أو اتصالًا بعيدًا. لو توجد مهمة READY_LOCAL واحدة فطابقها وأعلنها ونفذ النطاق المحلي المسموح؛ إذا لا توجد أو تعددت اسأل عن المهمة. ظهور ملف وحده لا يشغّل عملًا.
- التشغيل لا يغير HANDOFF أو يوسع نطاقه؛ يحدّث RESULT بنفس ID/Revision ويذكر ما تم فعلًا والآثار المجهولة. التطوير يراجع النتيجة ويحدّث قرار القبول والحالة، ولا يزوّر نتيجة باسم التشغيل.

## الرفع والنشر إن أجازهما المستخدم لاحقًا

التفويض صريح بالـcommit والوجهة/البيئة والإجراء؛ راجع أثر push على النشر والترحيلات/seeders. اتبع ترتيب المشروعين المحدد بالتسليم، لا ترتيبًا ثابتًا مفترضًا. تحقق بعد كل خطوة ولا تعاود إجراء قد يكرر كتابة بيانات قبل فحص أثر المحاولة السابقة. الاستعادة تحتاج تفويضًا مستقلًا؛ وجود backup ليس إذنًا بها. عند الفشل نفذ تراجعًا معتمدًا ومصرحًا فقط، وإلا قدم الأدلة وانتظر القرار.

## حدود الاستمرارية

الملفات تحفظ الاتفاق ولا تنقل ذاكرة المحادثات أو توقظ الوكلاء. الجلسة القديمة المفتوحة قد تحتاج رسالة «أعد قراءة AGENTS.md وملفات agent-handoff من المجلدين الأصليين ثم طبّق دورك» أو إعادة فتحها. لا يمكن لهذه الملفات تغيير سياق جلسة محمل سابقًا بالقوة، ولا ضمان التزام أداة لا تقرأ تعليمات المشروع. عند إنشاء worktree من فرع تاريخي تحقق من AGENTS.md؛ إن غاب اقرأ النسخة الأصلية وثبّت مدخل الإرشادات قبل العمل.
