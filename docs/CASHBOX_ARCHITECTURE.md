# CASHBOX_ARCHITECTURE.md — دستور معمارية نظام الخزن والسيولة النقدية (FAC-001)

---

## 📌 مقدمة
يوثق هذا المستند القواعد المعمارية الثابتة (Invariants)، ودورة حياة الخزن (Lifecycle)، وقواعد الأعمال التي تحكم نظام الخزن والسيولة النقدية في نظام HWNix ERP. 
الهدف: ضمان استقرار تام للعمليات المالية والنقدية ومنع أي فرصة لتسريب أو تعديل غير موثق للأرصدة.

---

## 🔄 1) دورة حياة الخزينة (CashBox Lifecycle)

تتم إدارة دورة حياة الخزينة بالكامل وحصرياً عبر `CashBoxLifecycleService`. يُمنع منعاً باتاً تعديل حقول الحالة أو نوع الوصول بشكل مباشر من أي مكان آخر.

```
       [ Draft ]
           │
           ▼
       [ Active ] <─────────┐ (Restore)
         │    │             │
         │    └─► [ Locked ]│
         ▼                  │
    [ Inactive ] ───────────┘
         │
         ▼
     [ Archived ]
```

### الحالات المعتمدة:
1. **مسودة (`draft`)**: مرحلة الإنشاء الأولي (الخزنة غير مستعدة بعد لتلقي أي حركات مالية).
2. **نشطة (`active`)**: الحالة الوحيدة التي يُسمح فيها بإجراء عمليات إيداع وسحب وتحويل نقدية.
3. **معطلة (`inactive`)**: مغلقة مؤقتاً للعمليات المالية. يتم تعطيل العهدة تلقائياً عند تعطيل الموظف أو سحب الصلاحيات.
4. **مغلقة للتدقيق (`locked`)**: قراءة فقط لقيم الأرصدة والعمليات السابقة؛ يُمنع تغيير الأرصدة خلال فترة التدقيق.
5. **مؤرشفة (`archived`)**: خزن مؤرشفة نهائياً (مثل الخزن القديمة التوافقية `legacy_archived`). لا يمكن إرجاعها للحالة النشطة إلا بعملية استعادة صريحة وموثقة.

## 🔐 2) قواعد العمل الثابتة (Business Invariants)

قواعد صارمة ومحمية برمجياً على مستوى طبقة النطاق والموديل (`CashBoxDomainRules` وحدث `updating` بموديل `CashBox`):

### قواعد الملكية والوصول:
* **العهدة الشخصية (`personal`)**: 
  * يجب أن ترتبط بموظف واحد فقط (`user_id !== null`).
  * يجب أن يمتلك الموظف قدرة `has_cash_custody` في الشركة.
  * لا يمكن أن تكون خزنة مشتركة بالوقت نفسه.
* **الخزنة المشتركة (`company_shared`)**:
  * لا ترتبط بموظف محدد (`user_id === null`).
  * يتم منح وسحب الصلاحية للموظفين حصرياً عبر الجدول الوسيط `cash_box_user`.
* **الافتراضية (`is_default`)**:
  * يتم تعيين الخزينة الافتراضية للموظف في حقل `users.default_cash_box_id` لضمان عزل وتلافي مشاكل الخزن المشتركة.
  * لا يجوز أن يمتلك الموظف أكثر من خزنة افتراضية واحدة في الشركة والفرع نفسه.

### قواعد نزاهة الأرصدة والعمليات المالية:
* **حظر التعديل المباشر للأرصدة**:
  * يُمنع منعاً باتاً تعديل حقل `cash_boxes.balance` عبر الـ Controllers أو Observers أو حتى الموديل مباشرة.
  * المسار الوحيد للتعديل هو `CashService` المستدعى من `FinancialEngine` داخل Transaction مؤمنة بـ `lockForUpdate`.
  * يتم فحص مسار الاستدعاء برمجياً (Debug Backtrace Check) عند كل تحديث للرصيد لرفض أي محاولة تلاعب.
* **ثبات الخصائص الجغرافية والشركات**:
  * الحقول `company_id` و `branch_id` غير قابلة للتغيير نهائياً بعد الإنشاء (`immutable`). عند انتقال الموظف لفرع آخر، يجب إغلاق الخزنة القديمة وإنشاء خزنة جديدة بالكامل.
* **حظر الحذف المادي**:
  * لا يمكن حذف أي خزنة من قاعدة البيانات نهائياً بعد إنشائها (`deleting` event block). الإجراء الوحيد المتاح هو التعطيل (`deactivate`) أو الأرشفة (`archive`).

## 📡 3) أحداث النطاق والأثر الجانبي (Events Policy)

* **الأحداث الجانبية**: يتم إطلاق أحداث النطاق (مثل `CashBoxCreated`, `DefaultCashBoxChanged`) للإجراءات الإدارية.
* **التدقيق**: يستمع `CashBoxActivityLogListener` للأحداث الإدارية لتسجيل الأنشطة وتتبع من منح صلاحية أو غيّر الافتراضيات بجدول التدقيق (`ActivityLog`).
* **حظر الاعتماد المالي للأحداث**: تُستخدم الأحداث حصرياً للمهام الجانبية (Logs, Notifications, Caching). أي عملية مالية أو تعديل للأرصدة يجب أن يتم بشكل متزامن داخل المعاملة نفسها (`DB::transaction`) لضمان الاتساق المحاسبي الفوري.

## 🧪 4) فحص السلامة المعمارية (Health Check)

يوفر النظام أداة فحص دورية عبر الأمر:
```bash
php artisan cashboxes:health-check
```
يقوم الأمر بمسح قاعدة البيانات وتحديد أي خروقات لقواعد المعمارية لتفادي أخطاء الدعم الفني مبكراً.
